# 条目约定

每收录一个仓库，新增一篇 `entries/OWNER-REPO.md`。分类页只留一行索引，判断和用法写在条目里。

语气像给以后的自己上课：短、具体、能照着做一遍。不复制上游 README，不堆形容词。

## 文件名

`entries/` 下的文件名为 `所有者-仓库名.md`，大小写与 GitHub 上的 owner / repo 一致。

示例：仓库 `huggingface/transformers` 对应 `entries/huggingface-transformers.md`。

所有者或仓库名本身若含连字符，文件名仍用单个 `-` 拼接。分类表里的详情链接是查找入口，不要从文件名反推仓库名。

## 模板

```markdown
# owner/repo

## 简介

一两句话：它是什么，解决什么问题。

## 适用场景

- 适合：什么样的任务或约束下会用它。
- 不适合：哪类需求该换别的工具，或先不要用。

## 快速用法

最小可运行的步骤或命令。注明对照的文档或版本位置；不确定的接口写成「未核实」，不要猜。

## 推荐理由

相比同类实现，它多解决了哪一点，所以留在这个合集里。

## 入库日期

YYYY-MM-DD

## 源链接

https://github.com/owner/repo

## 是否已 Star

是 / 否。只记录个人账号当时的状态（每周策展自动化入库时会代为点亮 Star）。
```

## 挂到分类页

在对应的 `categories/*.md` 表格末尾追加一行：

| 仓库 | 简介 | 入库日期 | 详情 |
| --- | --- | --- | --- |
| [owner/repo](https://github.com/owner/repo) | 一句话简介 | YYYY-MM-DD | [笔记](../entries/owner-repo.md) |

一个仓库只放一个主分类。若两条主线都沾边，放更贴近使用场景的那一页，另一页不重复收录。

## 写作时核对

- 简介控制在一两句，读者不点进源仓库也能判断要不要继续看。
- 快速用法只保留一条能跑通的路径，并指向源文档。
- 推荐理由写判断依据，不写「强大」「必备」这类空话。
- 命令、默认参数、许可证有疑问时标明「未核实」。
- 修订已有条目时，不要改掉原来的入库日期；把修订记进 `CHANGELOG.md`。
